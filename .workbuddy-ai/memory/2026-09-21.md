## Push y hallazgo del sandbox (mismo hilo)

### El "ahead 309" era un artefacto, no una divergencia

`git status` reportaba `[ahead 309]` contra `origin/main`, alarmante. **Falso.** Causa raíz: el
sandbox de este entorno **intercepta silenciosamente las escrituras de git a `.git/refs/`** (git
escribe refs con lockfile + rename; el sandbox se lo traga y git igual reporta éxito). Consecuencia:
`git fetch` descargaba objetos pero **el ref remoto local nunca se actualizaba** y quedaba clavado en
`packed-refs` (valor `5ad79e4`, de enero 2026). De ahí el "ahead 309".

**Diagnóstico correcto**: no confiar en el ref local; preguntar al remoto. `git ls-remote origin main`
y `git merge-base --is-ancestor <remoto> main` dieron la verdad: el remoto real estaba en `c01158c`,
ancestro de `main` → fast-forward limpio, **0 detrás / 7 adelante**.

**Fix del ref local**: `git update-ref` **no funciona** aquí (reporta ok, no escribe). Escribir el
archivo a mano sí:
```bash
mkdir -p .git/refs/remotes/origin
printf '37f3a6298b976c2b8313a81fbf6568cd4207192b\n' > .git/refs/remotes/origin/main
```
Tras eso `git status` quedó en `## main...origin/main`, sin ahead/behind.

### Push

`git push origin main` → `c01158c..37f3a62 main -> main` (exit 0). El hook `pre-push`
(`scripts/git_hooks/pre_push_guard.py`) solo bloquea reescrituras de historial; un fast-forward pasa.
Verificado con `git ls-remote`: remoto = `37f3a62` = local. Árbol limpio.

### Lección operativa (entorno Windows + sandbox)

Si `git status` muestra un ahead/behind raro: **no creerle al ref local**. Verificar con
`git ls-remote origin <rama>` (autoritativo) y `git merge-base --is-ancestor`. El ref local puede
mentir por escrituras de ref tragadas por el sandbox.
